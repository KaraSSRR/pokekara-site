How Pokekara Builds VITALE with Claude

VITALE: Football Career is a mobile football career RPG built on deeply connected simulation systems. Claude is part of how we engineer it: a force multiplier inside a human-controlled process that helps a small independent studio reason about, build, test and review a football world.

01Why Claude

VITALE is not a set of independent screens. It is a persistent football world where systems feed one another. A change to how a player develops can alter who gets selected, how many minutes they play, how tired they become, how well they perform, which clubs take notice and, eventually, the shape of an entire career.

  1. Player development
  2. Squad selection
  3. Minutes played
  4. Fatigue & form
  5. Performance
  6. Market interest
  7. Transfer opportunities
  8. Career trajectory

For a small team, the hard part is not writing any single feature. It is holding the whole system in view while changing one part of it. Claude helps us do that: it can read across a large repository, trace how systems connect, and reason about consequences before code changes — and then help implement, test and review those changes.

Our principle

AI-assisted engineering, human-controlled product. Claude expands what we can build. It does not decide what we build.

02Where Claude fits in VITALE

VITALE is built in three layers: headless simulation systems that decide what happens, a Unity mobile client that shows it, and a Blender production pipeline for characters and high-impact career moments. Claude works on the engineering side of that picture.

Simulation systems

MatchEngine, WorldEngine, career systems, competitions and transfers: the main place Claude helps with architecture, implementation, tests and review.

Data & tooling

Data pipelines, validation rules, diagnostics and the internal tools that keep a large world consistent.

QA

Regression analysis and deterministic checks across the systems above.

Product & creative direction

Game design, creative direction, scope and acceptance stay with people.

03The workflow

Every meaningful change follows the same path. Claude participates in most stages; humans own the first and the last.

  1. Product direction
  2. Architecture
  3. Implementation
  4. Automated testing
  5. Independent review
  6. Human acceptance

Humans own

  • Product direction and game design
  • Final architecture decisions
  • Scope — what is in and what is out
  • Final acceptance of every change

Claude assists with

  • Repository-scale analysis
  • Implementation and refactoring
  • Test creation and regression analysis
  • Code review and technical documentation
  • Decomposing large engineering objectives

04Architecture reasoning

Before implementation, we ask Claude to analyse the relevant parts of the repository: which systems are involved, where state lives, what depends on what, and which invariants must not break. This turns a vague objective into a concrete map of the change.

Claude proposes options and trade-offs; a human chooses. Architectural decisions are made by people and written down, so the next change starts from an explicit foundation rather than from memory.

05Implementation

Large objectives are decomposed into bounded tasks. Each task has an explicit scope, constraints and acceptance criteria, and Claude implements against that brief — not against an open-ended request.

# The shape of a typical task brief
OBJECTIVE    One bounded change, stated plainly
CONTEXT      Systems and files involved
CONSTRAINTS  Determinism holds · no unrelated changes
TESTS        New behaviour covered · existing suite passes
ACCEPTANCE   Review complete · human sign-off

Bounded changes are easier to review, easier to test and easier to revert. They also keep Claude's work focused on the part of the system the task is actually about.

06Test generation

Claude helps write automated tests alongside the code: unit tests for individual rules, scenario tests for multi-step simulation behaviour, and checks for edge cases a person might not think to try. Tests are treated as part of the change, not an afterthought.

Because simulation systems interact, many of the most valuable tests describe outcomes across systems — for example, that a fatigue change does not silently break selection logic further down the chain.

07Regression analysis

When a change touches shared systems, Claude helps identify what could regress and why. It reads test output and diagnostic logs that are too long to inspect comfortably by hand, groups failures by likely cause, and points to where behaviour diverged.

The goal is not just a green test run. It is understanding whether a changed result is a bug, an intended consequence, or a sign that a test needs to change — and that judgement stays with a human.

08Independent review

Implementation and review are kept separate. A review pass starts from a fresh context, reads the diff against the original brief, and is explicitly asked to challenge assumptions: missed edge cases, unintended side effects, scope creep, and places where the code does something other than what was asked.

Findings are verified before they are acted on. A human decides which findings matter.

09Deterministic validation

VITALE's MatchEngine is a headless simulation designed to be deterministic: given the same inputs and the same seed, it produces the same result. That property is what makes the simulation testable and balanceable over the long term.

We use it as a safety net. Changes that should not affect outcomes can be checked for exactly that, and changes that should affect outcomes can be measured rather than eyeballed. Claude helps write these checks and interpret where results differ.

10Data tooling

A football world needs a lot of structured data: player identity and roster data, physical profiles, clubs and competitions. Claude helps build and maintain the pipelines that shape, validate and load that data, and helps write the validation rules that catch inconsistencies before they reach the simulation.

11Multi-agent development workflows

For larger objectives, work is split across focused Claude sessions with different jobs — exploring the codebase, implementing a bounded task, running verification, or reviewing someone else's change. Separating roles keeps each context small and means the agent reviewing a change is not the one that wrote it.

A human coordinates the work, sets the scope of each task and integrates the results.

12Human acceptance

Nothing ships because a model said it was done. Every change ends with a human decision: does this do what the product needs, is the evidence convincing, and does it fit where VITALE is going? Product direction, design taste and final acceptance remain human-owned.

Claude helps a small team approach engineering problems that would conventionally need more engineering capacity. It does not replace engineers, and it does not own the product.

13Future Claude & API use
